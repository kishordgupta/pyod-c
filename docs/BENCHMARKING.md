# Comparing PyOD, pyod-c and pyod-rs

The README reports the published October 31, 2026 benchmark on an Apple M3 Max: PyOD 3.6.7 versus the C and Rust ports, median of three fresh-detector runs, `fit + decision_function`, with CSV loading excluded. Shared inputs were generated by PyOD with 10 features and 10% contamination. The small panel used 2,000 train / 1,000 test rows; the large panel used 20,000 train / 5,000 test rows.

| Original panel | C geometric-mean speedup | Rust geometric-mean speedup |
|---|---:|---:|
| 22 classical models, 2,000 training rows | 2.8x | 2.9x |
| 5 neural models, 2,000 training rows | 1.2x | 1.4x |
| 10 classical models, 20,000 training rows | 1.3x | 1.5x |

The small classical winner counts in the original report are C 11 / Rust 11 / PyOD 0; rounded table entries can tie. Preserve the unrounded measurements when computing winners in a new experiment.

A [CSV transcription](benchmarks/original_reported_timings.csv) preserves the displayed rounded timing table; it is not the original per-run data.

Original environment: NumPy 2.0.2 with Accelerate BLAS, scikit-learn 1.6.1, PyTorch 2.8.0 on CPU, numba 0.60, Rust 1.99.1 release mode, burn 0.22, Apple clang 21 at `-O2`. The original full cross-library runner and per-repeat records are not bundled here. The workflow below is an additional reproducible classical subset, not an exact reconstruction of that entire run.

## A reproducible shared-input subset

The same [benchmark_pyod.py](../scripts/benchmark_pyod.py) is included in both ports. It supports ABOD, COPOD, ECOD, HBOS, IForest, KNN, LOF and PCA, and can run PyOD alone or with either/both ports. Python is a benchmark dependency only; it is not required by the native libraries.

Clone the two repositories as sibling directories. From their parent directory:

```bash
git clone https://github.com/kishordgupta/pyod-c.git
git clone https://github.com/kishordgupta/pyod-rs.git
make -C pyod-c examples
cargo build --release --manifest-path pyod-rs/Cargo.toml --example benchmark_csv
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install pyod==3.6.7 numpy==2.0.2 scikit-learn==1.6.1 numba==0.60 threadpoolctl
python pyod-rs/scripts/benchmark_pyod.py   --c-root pyod-c --rs-root pyod-rs --out results/default   --repeats 3 --warmup 1
python pyod-rs/scripts/benchmark_pyod.py   --c-root pyod-c --rs-root pyod-rs --out results/one-thread   --threads 1 --repeats 3 --warmup 1
```

Use a new or empty output directory for each run. The script never overwrites a populated result directory. To check a larger panel, use `--train 20000 --test 5000 --models COPOD ECOD HBOS IForest KNN LOF PCA`; use `--features` and `--seed` to vary the shared input. The model seed is fixed at 42 for IForest in each backend; changing `--seed` changes the data, not that model seed.

The script generates data once in PyOD and writes 17-digit CSV values for both native helpers. It fits a fresh model per repetition after the specified warm-up count, records fit and scoring separately, and computes AUC/average precision outside the timer. It excludes imports, construction, CSV loading, process launch, output serialization, compilation and metric calculation. The C scoring timer includes allocation of its caller output buffer. It uses `perf_counter`, Rust `Instant`, and POSIX `CLOCK_MONOTONIC` for elapsed wall time.

The default warm-up removes many first-use/JIT costs. For cold-start latency, run separate fresh processes with `--warmup 0`, and measure process/import startup as a separate metric. The subset does not time model construction, so it cannot establish whole-process latency.

`--threads 1` sets backend environment variables before importing numerical libraries and uses threadpoolctl for supported pools. Backend-specific limits may not all be visible to threadpoolctl (including some Accelerate versions); inspect the saved configuration. Both native classical helpers are serial. Running models in fixed order can expose thermal/cache/order effects; repeat with controlled process order for stronger performance conclusions.

Each run produces:

| File | Contents |
|---|---|
| `train.csv`, `test.csv`, `test_labels.csv` | Shared synthetic data and evaluation labels |
| `manifest.json` | Data hashes, package versions, NumPy build/backend configuration, thread settings, native commit/binary hashes and dirty-worktree flags |
| `raw.jsonl` | Each measured repetition, raw test scores, times, AUC, average precision and numerical comparisons |
| `summary.csv` | Median fit, score and total time; timing range; quality and score agreement; speedup |

Compile-time flags and hardware/power settings are not inferred by the script. Record them with your results, along with any manual model changes. Run on an otherwise idle machine and avoid comparing a debug native build with an optimized Python backend.

The supplementary November 2 local verification in [verification_2026-11-02](benchmarks/verification_2026-11-02/) uses this eight-model subset and has separate provenance. It does not replace or expand the original M3 Max panels.

## Interpreting speed and quality

For one model, `speedup = median(PyOD fit+score) / median(port fit+score)`. A ratio of 2 means half the elapsed time; 0.5 means twice the elapsed time. Compute the median of each repetition's total, rather than summing independently computed medians of fit and scoring.

Use the geometric mean of per-model ratios to summarize a fixed panel. A geometric mean does not weight models by production frequency, training frequency, number of requests or absolute seconds. Calculate application savings from the operations your application actually performs. A 10x gain on a sub-millisecond step can matter less than a 10% regression on a long-running step.

Thread settings can reverse conclusions. In the original small-data table, PyOD GMM is 11 ms by default but 1.4 ms with one thread; C is 1.0 ms and Rust is 2.0 ms. Always identify which baseline column supplied a quoted speedup.

Performance also depends on search strategy, dimensions, precision, parallelism, BLAS/backend, initialization and training settings. Rust neural tensors are f32 internally; C neural code is double precision. These results compare implementations and configurations, not language alone. They do not measure GPU speed, peak memory, energy, throughput under concurrency or production reliability.

`summary.csv` checks the seven deterministic models against PyOD with `rtol=1e-7, atol=1e-8`. IForest is excluded from elementwise equality because of score-convention and random-stream differences; inspect its ranking metrics. These tolerance checks cover the generated fixture, not every parameter combination or edge case.

Validate score direction, thresholds and output quality before interpreting a faster runtime. Equal scores can preserve poor accuracy: the November 2 fixture gives LOF an AUC of about 0.206 in all three implementations. This is consistent behavior on that generated dataset, not a reason to invert scores after inspecting test labels. Use validation data to choose a model and orientation, then evaluate on a separate test set.
